# PoolAI: Оптимізована система розподілених обчислень

## 0. Майнінг нового покоління

### 0.1 Визначення
Майнінг нового покоління - це процес використання обчислювальних ресурсів (CPU, GPU, DPU, ASIC) для обробки запитів генеративних нейронних мереж. На відміну від традиційного майнінгу криптовалют, де обчислювальна потужність спрямована на вирішення криптографічних задач, новий майнінг фокусується на генерації корисного контенту та вирішенні реальних задач.

### 0.2 Компоненти майнінгу
- **Обчислювальні ресурси**: CPU для загальних задач, GPU для паралельних обчислень, DPU для спеціалізованих операцій, ASIC для оптимізованих задач
- **Генеративні моделі**: Нейронні мережі для створення тексту, зображень, коду та інших типів контенту
- **Розподілена обробка**: Пул воркерів для ефективного розподілу навантаження
- **Система винагород**: Нагороди за якість та швидкість генерації контенту

### 0.3 Переваги нового майнінгу
- Корисний вихід: генерація реального контенту замість абстрактних обчислень
- Гнучкість: можливість перемикання між різними типами задач
- Ефективність: оптимізація використання ресурсів під конкретні задачі
- Масштабованість: легкість додавання нових воркерів та типів задач

### 4.3 HTTPS/TLS Архитектура

#### 4.3.1 Варианты развертывания

**Вариант A: Встроенный HTTPS (Рекомендуется для production)**
```
Internet → PoolAI (HTTPS:443) → Internal Services
         ↑
   TLS termination в PoolAI
   - Let's Encrypt автоматическое обновление
   - Self-signed для разработки
   - Wildcard сертификаты для поддоменов
```

**Вариант B: Reverse Proxy (Рекомендуется для enterprise)**
```
Internet → Nginx/Apache (HTTPS:443) → PoolAI (HTTP:8080)
         ↑
   TLS termination в Nginx
   - Централизованное управление сертификатами
   - Load balancing
   - Дополнительная защита
```

#### 4.3.2 Этапы реализации HTTPS

**Этап 1: HTTP для разработки (MVP)**
- HTTP на localhost:8080
- Базовая аутентификация
- Подготовка архитектуры для HTTPS

**Этап 2: HTTPS для тестирования (Stage 2)**
- Self-signed сертификаты
- Встроенная TLS поддержка
- Тестирование в staging среде

**Этап 3: Production HTTPS (Stage 3)**
- Let's Encrypt автоматические сертификаты
- HSTS заголовки
- Perfect Forward Secrecy
- Certificate Transparency

#### 4.3.3 Конфигурация безопасности

```toml
[security]
# TLS/HTTPS настройки
enable_https = true
cert_path = "/etc/poolai/certs/cert.pem"
key_path = "/etc/poolai/certs/key.pem"
redirect_http_to_https = true

# Аутентификация
jwt_secret = "your-super-secret-key"
jwt_expiration = 3600  # 1 час
rate_limit_requests = 100  # запросов в минуту
rate_limit_window = 60  # секунд

# CORS настройки
cors_origins = ["https://poolai.example.com"]
cors_methods = ["GET", "POST", "PUT", "DELETE"]
cors_headers = ["Authorization", "Content-Type"]

# Безопасность заголовков
security_headers = true
hsts_max_age = 31536000  # 1 год
content_security_policy = "default-src 'self'"
```

## 9.5 Архітектурні принципи Rust

### 9.5.1 Zero-Cost Abstractions
- Trait-based поліморфізм без накладних витрат часу виконання
- Компілятор оптимізує абстракції до нативного коду
- Zero-copy операції де можливо

### 9.5.2 Безпека пам'яті без GC
- Ownership та Borrowing для безпечного управління пам'яттю
- Arc<RwLock<T>> для розділяємого змінюваного стану
- Lifetimes запобігають висячим вказівникам

### 9.5.3 Concurrency-First Design
- Async/await для неблокуючих операцій (Network Module - 100%)
- Tokio runtime для багатопотоковості (Runtime Module - 100%)
- Actor model для ізоляції стану (Core Module - 100%)

### 9.5.4 Type Safety
- Строга типізація запобігає помилкам часу виконання
- Pattern matching для вичерпної обробки
- Option<T> та Result<T, E> для обробки помилок (Core Error Module - 100%)

## 9.7 Rust Best Practices

### 9.7.1 Організація модулів
- Кожен модуль має файл `mod.rs` як точку входу (15 модулів - 100%)
- Підмодулі оголошуються в `mod.rs` та реалізуються в окремих `.rs` файлах
- Публічний API реекспортується через `pub use` statements
- Деталі реалізації зберігаються в підмодулях

### 9.7.2 Обробка помилок (Core Error Module - 100%)
- Всі функції, які можуть завершитися помилкою, повертають `Result<T, AppError>`
- Типи помилок визначені в модулі `core::error`
- Помилки поширюються за допомогою оператора `?`
- Panic використовується тільки для невідновлюваних помилок

### 9.7.3 Concurrency (Runtime Module, Network Module - 100%)
- Розділяємий стан використовує `Arc<RwLock<T>>` для потокобезпечного доступу
- Async функції використовують `tokio::sync::RwLock` для async контекстів
- Передача повідомлень через канали (`mpsc`, `oneshot`) для комунікації
- Фонові задачі запускаються з `tokio::spawn`

### 9.7.4 Управління пам'яттю (VM Module - 100%)
- Ownership явний та перевіряється на етапі компіляції
- Borrowing використовується для тимчасового доступу
- `Arc` використовується для розділяємого володіння між потоками
- Lifetimes запобігають висячим посиланням

### 9.7.5 Тестування (410+ passing: 102 unit + 308+ integration)
- Unit тести в `#[cfg(test)]` модулях (102 unit tests)
- Integration тести в директорії `tests/` (308+ integration tests)
- Mocking для зовнішніх залежностей
- Property-based тестування з `proptest`

## 11. Среда разработки и сборка

### 11.1 Вимоги до середовища

#### 11.1.1 Windows (Рекомендовано)
- **MSYS2 UCRT64** - основне середовище розробки та компіляції
- **Rust toolchain**: `stable-x86_64-pc-windows-gnu` (GNU toolchain)
- **MSYS2 UCRT64 shell** - автоматично використовується в Cursor/VS Code терміналі
- **GCC/MinGW-w64** - надається MSYS2 UCRT64

**Важливо**: Для збірки з features `enterprise,https,jwt` потрібен MSYS2 GCC в PATH.  
Використайте скрипт `scripts/build-with-https.sh` або встановіть змінні оточення:
```powershell
$env:PATH = "C:\msys64\ucrt64\bin;C:\msys64\usr\bin;$env:PATH"
$env:CC = "gcc"
$env:CXX = "g++"
cargo build --features enterprise,https,jwt
```

#### 11.1.2 Конфігурація терміналу
Проект налаштований для автоматичного використання MSYS2 UCRT64 оболонки:
- Файл `.vscode/settings.json` містить налаштування терміналу
- Термінал автоматично запускається в MSYS2 UCRT64 при відкритті нового терміналу
- Змінні оточення `MSYSTEM=UCRT64` та `CHERE_INVOKING=1` встановлені автоматично

#### 11.1.3 Rust Toolchain Setup

**Якщо Rust не знайдено в MSYS2 UCRT64** (`cargo: command not found`):

1. **Додати Rust в PATH** (якщо Rust вже встановлено в Windows):
```bash
# Додати в ~/.bashrc або ~/.bash_profile
echo 'export PATH="/c/Users/$USER/.cargo/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc
```

2. **Або встановити Rust через rustup в MSYS2**:
```bash
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
export PATH="$HOME/.cargo/bin:$PATH"
```

3. **Встановлення GNU toolchain**:
```bash
# Встановлення GNU toolchain для MSYS2
rustup default stable-x86_64-pc-windows-gnu

# Або для конкретного проекту
rustup override set stable-x86_64-pc-windows-gnu
```

4. **Перевірка встановлення**:
```bash
cargo --version
rustc --version
rustup show
```


### 11.3 Переваги MSYS2 UCRT64
- **Сумісність**: Повна сумісність з Windows API через UCRT (Universal C Runtime)
- **Продуктивність**: Оптимізовані бінарники для Windows
- **Бібліотеки**: Легкий доступ до бібліотек через pacman (менеджер пакетів MSYS2)
- **Інтеграція**: Плавна інтеграція з сучасними інструментами розробки
- **Відлагодження**: Підтримка GDB та інших інструментів відлагодження

### 11.4 Альтернативні середовища
- **Linux**: Нативна компіляція через стандартний Rust toolchain
- **WSL**: Можна використовувати, але рекомендовано MSYS2 UCRT64 для Windows
- **MSVC**: Не рекомендовано через проблеми з залежностями (ring, gcc.exe)
