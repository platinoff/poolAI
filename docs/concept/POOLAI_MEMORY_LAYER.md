# PoolAI Memory Layer — AGI‑памʼять та Seeds (v1, 2026-03-17)

## 1. Ідея

PoolAI вже має:

- **RAID + Event Sourcing** — надійне розподілене сховище артефактів.
- **ML.1–ML.6** — Pruning, AutoML, Federated Learning, Context Memory Monitoring.

Цей документ описує, як ці компоненти разом утворюють **Memory Layer**:

- “спогади” / ембедінги / моделі = артефакти в RAID;
- оновлення памʼяті = ML‑пайплайни;
- доступність знань = наявність “сідсів” (нод, що тримають shards).

## 2. Памʼять як артефакти в RAID

- Кожен **артефакт** (файл, модель, ембедінг, snapshot) уже зараз:
  - зберігається в RAID з Burst/SmallWorld‑стратегіями;
  - має історію через Event Sourcing.

**Memory Layer** трактує:

- “AGI‑памʼять” = набір артефактів/ембедінгів/моделей, які:
  - мають стабільні ідентифікатори (ID, версії);
  - реплікуються між нодами згідно RAID‑політики.

## 3. Seeds і поведінка “як торент”

Аналогія з торентами:

- **Seed** = нода, яка тримає shard певної памʼяті (артефакту/моделі/ембедінгів) і готова віддавати його іншим.
- **Availability**:
  - якщо є достатньо сідсів → знання/LLM‑функція доступна;
  - якщо сідсів немає → відповідна функція **тимчасово недоступна** (нема звідки завантажити state).

RAID/SmallWorld уже дає:

- шардінг і реплікацію;
- метрики й топологічно усвідомлений розподіл.

Memory Layer додає **семантику AGI‑памʼяті** поверх існуючої реалізації.

## 4. ML‑модулі як механізм оновлення памʼяті

- **Pruning / Quantization / Optimization (ML.1)**:
  - змінюють форму/розмір памʼяті (менші/ефективніші моделі й ембедінги).

- **AutoML (ML.2)**:
  - підбирає кращі моделі/гіперпараметри → нові версії “сідсів”.

- **Federated Learning (ML.3)**:
  - агрегує локальні оновлення від нод без централізованого збору даних;
  - оновлює глобальні “сідси” моделі.
  - У **ML.6** окремий крок пайплайну **`FederatedAggregation`** може застосовувати ту ж семантику агрегації всередині оркестрації (поряд із AutoML, pruning тощо).

- **Context Memory Monitoring**:
  - відстежує використання памʼяті (частота, розмір, ефективність);
  - дає підказки, що потрібно “очищати”/переносити/реплікувати.

Таким чином, ML‑модулі = **фабрика оновлень памʼяті**, RAID = **носій**, ноди = **сідси**.

**Операційний доступ (2026‑03)**: за фічами `enterprise` + `ml` HTTP **`/api/enterprise/ai-ml/pipeline`** дозволяє оголошувати й виконувати пайплайни на спільному **`MLPipelineManager`** у контексті API (див. `src/network/api/ai_ml.rs`). Помилки цих маршрутів — той самий JSON-конверт **`error` / `context`**, що й для `/api/v1/*` (**`HttpAppError`**, **`RestError`** за FM-005; див. `docs/catalog/FUNCTION_MANAGEMENT.md`).

## 5. Звʼязок з Grid / Job Layer

- **Job Layer**:
  - jobs можуть бути як “обчислення”, так і “операції з памʼяттю”:
    - завантажити/оновити shard,
    - перерахувати ембедінги,
    - виконати federated‑раунд.

- **Grid Layer**:
  - розповсюджує інформацію про те, **які ноди які сідси тримають**;
  - координує, де виконувати jobs, повʼязані з памʼяттю (ближче до потрібних shards).

## 6. Майбутня токенізація (Solana)

У майбутньому, Memory Layer може бути повʼязаний із Solana‑adapter‑ом:

- **Події**:
  - `SeedProvided` — нода тримає shard і обслуговує запити;
  - `SeedUpdated` — нода оновила shard (результат ML‑пайплайну);
  - `SeedRecovered` — нода допомогла відновити shard для інших.

Ці події можуть:

- конвертуватись у винагороди для нод;
- використовуватись для обліку внеску в **AGI‑памʼять**.

**Wire types (S38):** `src/memory/` (`MemoryShardRef`) ↔ `GridEnvelope` memory_shard. Деталі адаптера — [`SOLANA_ADAPTER_CONCEPT_2026-04-06.md`](../development/SOLANA_ADAPTER_CONCEPT_2026-04-06.md).

**HTTP (FM-022):** `GET/POST /api/v1/memory/shards`, `GET /api/v1/memory/shards/{shard_id}`; `POOLAI_MEMORY_DATA_DIR` → `shards.json`; filter `?raid_logical_name=` для RAID map.
