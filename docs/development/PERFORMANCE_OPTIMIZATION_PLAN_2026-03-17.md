# 🎯 План Оптимізації Продуктивності PoolAI (2026-03-17)

**Статус проекту**: v0.2.2, всі модулі 100% завершені, система production ready.  
**Мета цього плану**: дати **короткий, практичний** список кроків для оптимізації продуктивності з урахуванням глибокої логіки та потенційних bottleneck-ів, описаних у документації та бенчмарках.

---

## 1. Tokio Runtime та асинхронний пул задач

- **Концепція**: `tokio` runtime керує всіма async-операціями; невдалий підбір `worker_threads` / `max_blocking_threads` легко створює bottleneck.
- **Ціль**: підібрати значення так, щоб:
  - CPU-інтенсивні задачі не блокували I/O;
  - блокуючі операції (диск, мережа, сторонні SDK) не висіли в чергах.

**Кроки**:
- **1.1. Виміряти**:
  - Увімкнути детальні метрики runtime через існуючий `MetricsCollector` (CPU, latency, queue depth).
  - Прогнати навантаження (`wrk` / `hey` проти основних API) з поточною конфігурацією.
- **1.2. Протестувати варіанти**:
  - `TOKIO_WORKER_THREADS = num_cpus` (8, 16…) + `TOKIO_BLOCKING_THREADS = 4×workers`.
  - Порівняти p95/p99 latency та RPS.
- **1.3. Зафіксувати профіль**:
  - Описати **рекомендований профіль** для:
    - невеликих інсталяцій (4–8 vCPU),
    - середніх (16–32 vCPU),
    - великих (40+ vCPU).

**Результат**: окремий розділ “Tokio Profiles” у `docs/performance/TUNING.md` з конкретними значеннями змінних оточення.

## 2. Глобальний стан (`AppState`) та блокування

- **Концепція**: глобальний `AppState` побудований на `Arc<RwLock<...>>` + глобальному `state_mutex` для атомарних оновлень; часті/довгі записи можуть лімітувати паралелізм.

**Кроки**:
- **2.1. Виміряти контенцію**:
  - Додати легкі трейс-метрики:
    - час очікування на `RwLock::write`,
    - час утримання `state_mutex`.
  - Записувати ці метрики в Prometheus (через існуючий monitoring-модуль).
- **2.2. Виявити гарячі точки**:
  - Знайти операції, які:
    - часто беруть `write`-лок на всьому AppState;
    - довго утримують `state_mutex` (наприклад, масові оновлення worker-ів чи topology).
- **2.3. Рефакторинг блокувань (при потребі)**:
  - Розбити один великий `RwLock` на декілька більш дрібних (наприклад, окремо для:
    - worker pool,
    - topology,
    - cache state).
  - Замінити “грубий” `Mutex` для глобального state на більш локальні механізми (per-subsystem locks, CAS-структури, канали).

**Результат**: оновлена концепція глобального стану в `docs/ARCHITECTURE_BEST_PRACTICES.md` з розділом “Locking Strategy & Contention Mitigation”.

## 3. Обробка запитів моделей, кэш та ключі (`ModelRequest` / `ModelResponse`)

- **Концепція**: кожен запит моделі створює/клонувує структури запиту/відповіді і генерує cache-key (hash кількох полів). При високій пропускній здатності це може стати суттєвими накладними витратами.

**Кроки**:
- **3.1. Запустити існуючі бенчмарки**:
  - `bench_model_request_response`,
  - `bench_cache_key_generation`
  - з `benches/runtime_benchmarks.rs`.
- **3.2. Оптимізувати**:
  - Мінімізувати кількість алокацій у `ModelRequest` / `ModelResponse` (замість `String` там, де достатньо `&'static str` чи `Cow`).
  - Перевірити, чи можна зменшити кількість полів, що потрапляють у hash (баланс між унікальністю та швидкістю).
  - Впровадити `SmallVec` / пулізовані буфери для часто використовуваних структур, якщо це виправдано результатами бенчмарків.

**Результат**: оновлений розділ “Model Request/Response & Caching” у `docs/performance/BENCHMARKS.md` з новими цифрами до/після.

## 4. MemoryPool та LRU Cache

- **Концепція**: `MemoryPool` і LRU cache (`CacheManager`) критичні для пропускної здатності; неефективні `acquire/release` чи повільні `get/put` → додаткова латентність для кожного запиту.

**Кроки**:
- **4.1. Перезапустити бенчмарки**:
  - `bench_memory_pool_acquire_release`,
  - `bench_lru_cache_operations`.
- **4.2. Налаштувати розміри**:
  - Підібрати:
    - розмір пулу пам’яті,
    - розмір LRU cache,
    - політику TTL,
  - на реалістичних сценаріях навантаження.
- **4.3. Оптимізувати алгоритми**:
  - Перевірити, чи немає зайвих копіювань; де можливо, використовувати `Arc`/`&[u8]` замість копій.
  - Переконатися, що операції `get/put` є O(1) та мінімізують блокування (lock-free структури або шардований cache, якщо потрібно).

**Результат**: короткий “Sizing Guide” у `docs/performance/TUNING.md` (рекомендовані значення для cache/pool під різні профілі навантаження).

## 5. Обробка помилок, відновлення та їх вплив на продуктивність

- **Концепція**: система має багатий `AppError` / `PoolAIError` / `CursorError` та recovery-механізми. Якщо помилок багато, або recovery “важкий” — це витрачає CPU/IO та знижує пропускну здатність.

**Кроки**:
- **5.1. Аналіз метрик помилок**:
  - Використати `ErrorMetrics`:
    - частота помилок по категоріях;
    - час відновлення;
    - відсоток успішних recovery.
- **5.2. Категоризація гарячих сценаріїв**:
  - Виявити топ-3 типи помилок за частотою.
  - Для кожного — оцінити, чи відновлення:
    - не дублює важкі операції (повторні завантаження моделей, повторні мережеві запити тощо),
    - може бути зроблене більш легким (кешований стан, експоненційний backoff).
- **5.3. Оптимізація recovery-політик**:
  - Для частих “м’яких” помилок (тимчасові мережеві): гарантувати обмеження retry (max attempts, jitter).
  - Для “жорстких” помилок (конфігурація, несумісність): швидко fail-ити без зайвих спроб.

**Результат**: додати розділ “Error Budget & Recovery Policies” у `docs/core/error_handling.md` (або створити новий документ, якщо ще немає).

## 6. Сетевий рівень та discovery

- **Концепція**: модуль `discovery` (UDP broadcast + heartbeat + cleanup) та topology-побудова можуть стати вузьким місцем у великих кластерах.

**Кроки**:
- **6.1. Заміряти**:
  - Обсяг UDP-трафіку при реалістичній кількості вузлів.
  - Час виявлення нових/впавших пірів.
- **6.2. Оптимізувати інтервали**:
  - Переглянути періодичність heartbeat/cleanup з урахуванням:
    - бажаного часу виявлення (SLO),
    - максимально допустимого мережевого трафіку.
- **6.3. Покращити latency-метрики**:
  - Для `measure_latency` (TCP) встановити тайм-аути і ліміти паралельних перевірок, щоб не блокувати інші операції.

**Результат**: секція “Discovery Tuning” у `docs/performance/TUNING.md` з рекомендованими інтервалами/тайм-аутами.

## 7. Балансування навантаження та автоскейлінг воркерів

- **Концепція**: `LoadBalancingStrategy` + `select_worker` + автоскейлінг визначають, як рівномірно розподіляється трафік і як швидко додаються/знімаються воркери.

**Кроки**:
- **7.1. Збір метрик**:
  - Для кожного воркера:
    - завантаження CPU/пам’яті;
    - довжина черг;
    - кількість активних з’єднань (для стратегій типу LeastConnections).
- **7.2. Порівняння стратегій**:
  - На staging-кластері прогнати:
    - RoundRobin,
    - LeastConnections,
    - Weighted,
  - для однакових сценаріїв навантаження, оцінити:
    - дисперсію завантаження між воркерами;
    - середню та p95 латентність.
- **7.3. Налаштування автоскейлінгу**:
  - Переглянути `scaling_threshold`, cooldown-інтервали, мін/макс кількість воркерів.
  - Зафіксувати окремі профілі для:
    - latency-sensitive (швидкий масштабинг, агресивні пороги),
    - throughput-oriented (повільніший, стабільніший масштабинг).

**Результат**: розділ “Worker Pool Scaling Profiles” у `docs/performance/TUNING.md` + оновлення опису логіки в `docs/status/IMPROVEMENTS_2026.md` (або аналогічному статус-документі).

## 8. Моделі та ML-оптимізації (Stage 4.4)

- **Концепція**: нині модуль `ml/optimization` містить заглушки; відсутність справжньої оптимізації (quantization, pruning, tuning) означає, що моделі можуть бути суттєво важчими/повільнішими, ніж потрібно.

**Кроки (опціонально, але високий вплив)**:
- **8.1. Реалізувати базовий quantization**:
  - Для 1–2 ключових моделей додати:
    - post-training quantization,
    - виміряти вплив на latency/пам’ять.
- **8.2. Реалізувати simple pruning**:
  - Додати конфігураційний рівень (наприклад, “aggressive/medium/light”) і тестувати на окремих воркерах.
- **8.3. Оновити документи**:
  - `docs/ml/AUTOML.md` та `docs/status/AUTOML_IMPLEMENTATION_2026-01-22.md` — описати реальний стан (що вже не stub) та recommended workflow (profiling → quantization → optional pruning).

**Результат**: перший реальний приріст продуктивності на рівні моделей, задокументований як частина Stage 4.4.

## 9. Конкретні наступні кроки (сьогодні → 2 тижні)

**Порядок з урахуванням релевантності та глибокої логіки**:

   - Перезапустити бенчмарки з `benches/runtime_benchmarks.rs` (request/response, cache, memory pool, LRU).  
   - Зафіксувати поточні цифри у `docs/performance/BENCHMARKS.md` (baseline).
2. **Далі (3–5 днів)**  
   - Підібрати та задокументувати **Tokio runtime профілі** (розділ у `TUNING.md`).  
   - Додати/оновити метрики контенції для `AppState` і задокументувати стратегію блокувань.
3. **Наступний тиждень (5–10 днів)**  
   - Оптимізація `ModelRequest` / `ModelResponse` + cache-ключів на основі бенчмарків.  
   - Налаштування MemoryPool / LRU cache (розміри, TTL) для основних сценаріїв.  
   - Оновлення `TUNING.md` практичними “recipes”.
4. **Середньостроково (2–4 тижні, опціонально)**  
   - Тюнінг discovery та worker-pool scaling (спільні експерименти з реальним кластером).  
   - Перші кроки по Stage 4.4: quantization для 1–2 моделей + оновлення ML-доків.
